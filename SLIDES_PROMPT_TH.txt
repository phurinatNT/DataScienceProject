คัดลอกข้อความทั้งหมดนี้เพื่อสั่ง AI ทำสไลด์ โดยแนบ ZIP โปรเจกต์ StayWise และ Dataset หากระบบรองรับไฟล์

คุณเป็นผู้ออกแบบสไลด์และผู้ช่วยสอน Data Science ช่วยสร้างสไลด์ภาษาไทย 14 หน้า อัตราส่วน 16:9 สำหรับนักศึกษาวิทยาการคอมพิวเตอร์ นำเสนอ 10–12 นาที เรื่อง “StayWise: การทำนายการยกเลิกการจองโรงแรมด้วย Machine Learning” ผู้จัดทำ ภูริณัฐ สมศรี

เป้าหมายการนำเสนอ
- เกณฑ์อาจารย์ส่วนที่ 1: เตรียมข้อมูลถูกต้อง เข้าใจและอธิบายข้อมูลได้ รวมทั้งบอกว่าวิเคราะห์เพื่ออะไร (10 คะแนน)
- ส่วนที่ 2: ทำโมเดลและทดสอบ อธิบายว่าแม่นยำหรือไม่ และเพราะอะไร (5 คะแนน)
- เน้นให้ผู้ฟังเข้าใจกระบวนการและเหตุผล ไม่เน้นท่องศัพท์หรือแสดงโค้ดยาว

การออกแบบ
ใช้พื้นขาวหรือฟ้าอ่อน หัวข้อสีน้ำเงินเข้ม สีฟ้าสำหรับไม่ยกเลิก สีส้มสำหรับยกเลิก ให้สอดคล้องกับเว็บ StayWise ฟอนต์ไทยอ่านง่าย เช่น Sarabun หรือ IBM Plex Sans Thai หัวข้อ 30–36 pt เนื้อหา 22–26 pt หนึ่งสไลด์มีประเด็นหลักเดียว ไม่เกิน 3–5 bullet และไม่ใส่ย่อหน้ายาว ใช้แผนภาพ ตาราง และกราฟตามความเหมาะสม กราฟทุกกราฟต้องระบุจำนวน หน่วย และฐานข้อมูลที่ใช้ ไม่ใช้ภาพตกแต่งจนแย่งพื้นที่เนื้อหา

กติกาด้านความถูกต้อง
1. ใช้เฉพาะข้อเท็จจริงและผลทดลองด้านล่าง ห้ามแต่งค่าความแม่นยำ เพิ่มโมเดล หรืออ้างงานวิจัย/โรงแรมที่ไม่มีแหล่งข้อมูล
2. ระบุว่าเป็น Dataset สำหรับงานเรียน มีการใส่ปัญหาคุณภาพข้อมูลบางส่วนไว้โดยตั้งใจ ไม่อ้างว่าเป็นข้อมูลลูกค้าของโรงแรมจริงแห่งใด
3. ผลโมเดลเป็นการทดลองใหม่จากไฟล์นี้ ไม่ใช่ผลจาก hotel_model.pkl เดิม
4. ความสัมพันธ์จาก EDA ไม่ใช่เหตุและผล ห้ามสรุปว่าจ่ายมัดจำแล้วจะไม่ยกเลิกแน่นอน
5. ชุด Test ใช้ประเมินหลังเลือกพารามิเตอร์แล้ว ไม่ใช้ปรับพารามิเตอร์หรือเลือก Features
6. คะแนนหน้าเว็บเป็นคะแนนของต้นไม้ที่ถ่วงน้ำหนักคลาส ไม่ใช่เปอร์เซ็นต์ความน่าจะเป็นที่ผ่านการปรับเทียบ
7. ผลทดลองนี้ยังไม่เพียงพอสำหรับตัดสินใจแทนโรงแรม ห้ามอ้างว่าโมเดลแม่นยำสูงหรือพร้อมใช้เชิงพาณิชย์

ข้อมูลและผลจริงที่ต้องใช้
Dataset: C09_hotel_cancellation_classification(1).xlsx มีชีต Raw_Data, Data_Dictionary, Assignment
ข้อมูลดิบ 1,062 แถว 8 คอลัมน์ หนึ่งแถวแทนการจองหนึ่งรายการ ลบแถวซ้ำทั้งแถว 12 แถว เหลือ 1,050 รายการ และ booking_id ไม่ซ้ำ
ตัวแปร 8 คอลัมน์:
- booking_id: รหัสการจอง เป็น Identifier ใช้ตรวจซ้ำ ตัดออกจากโมเดล
- lead_days: จำนวนวันจองล่วงหน้าก่อนเข้าพัก เป็น Feature ตัวเลข
- nights: จำนวนคืน เป็น Feature ตัวเลขจำนวนเต็ม
- guests: จำนวนผู้เข้าพัก เป็น Feature ตัวเลขจำนวนเต็ม
- special_requests: จำนวนคำขอพิเศษ เป็น Feature ตัวเลขจำนวนเต็ม 0 หมายถึงไม่มีคำขอ
- deposit_paid: จ่ายมัดจำหรือไม่ เป็น Feature หมวดหมู่ Yes/No
- room_type: Standard, Deluxe, Family เป็น Feature หมวดหมู่ที่ไม่มีลำดับ
- cancelled: Target 0 = ไม่ยกเลิก, 1 = ยกเลิก
รวมใช้ 6 Features ก่อน Encoding และ Target 1 ตัว

ค่าว่างเดิม: lead_days 5, nights 4, guests 3, special_requests 4, deposit_paid 8, room_type 4; booking_id และ cancelled ไม่มีค่าว่าง
ความไม่สม่ำเสมอ: Yes/YES/yes และช่องว่างส่วนเกิน รวมถึง Standard/standard แก้ด้วย strip และ lower
ค่าที่น่าสงสัย: nights 5.4 และ 3.6, guests 4.8, special_requests 3.6 เป็นจำนวนที่ควรเป็นจำนวนเต็ม จึงเปลี่ยน 4 ค่านี้เป็นค่าว่าง ไม่ปัดเศษเดา แล้วเติมค่าภายหลัง
lead_days มีทศนิยมและสูงสุด 182.4 วัน ยังเก็บไว้เพราะอาจเป็นระยะเวลาจริง ไม่ลบเพียงเพราะค่าสูง ต้องตรวจต้นทางก่อนยืนยันว่าผิด
หลังลบซ้ำ cancelled=0 จำนวน 802 (76.38%), cancelled=1 จำนวน 248 (23.62%)

การเตรียมข้อมูลเพื่อโมเดล:
ลบซ้ำและแก้รูปแบบตามกฎความหมาย → แยก X/y และตัด booking_id → แบ่ง Train/Test แบบ Stratified 80/20, random_state=42 → ใช้ Pipeline เติมตัวเลขด้วย Median และหมวดหมู่ด้วยค่าที่พบบ่อยที่สุด (Mode) → One-Hot Encoding → Scaling เฉพาะ KNN → Cross-validation และฝึก → ประเมิน Test
เรียนรู้ Median/Mode/Encoding/Scaling เฉพาะ Training Fold ภายใน Cross-validation; fit ชุด Train ทั้งหมดหลังเลือกพารามิเตอร์แล้ว ไม่เรียนรู้จาก Test
การทดลองนี้ไม่ได้ทำ Feature Selection แบบอัตโนมัติ ใช้ Features ทั้ง 6 ตัวหลังตัด Identifier หากจะทำเพิ่ม ต้องทำภายใน Training Fold
Median จาก Train หลังแก้ค่าจำนวนที่ผิด: lead_days=63, nights=4, guests=3, special_requests=2
room_type ใช้ One-Hot เพราะไม่มีลำดับ ไม่แทนด้วย 1,2,3 ให้เกิดลำดับเทียม; การทดลองนี้ใช้ One-Hot กับ deposit_paid ด้วย
KNN ใช้ StandardScaler เพราะคำนวณระยะห่าง; Decision Tree ไม่จำเป็นต้อง Scaling

EDA หลังลบซ้ำ ก่อนเติมค่าว่าง:
- ไม่จ่ายมัดจำ: 523 รายการ ยกเลิก 200 = 38.24%
- จ่ายมัดจำ: 519 รายการ ยกเลิก 48 = 9.25%
- ไม่รวม 8 รายการที่สถานะมัดจำว่างในการคำนวณแยกกลุ่มนี้
- วันจองล่วงหน้าเฉลี่ย: กลุ่มยกเลิก 73.06 วัน กลุ่มไม่ยกเลิก 57.69 วัน คำนวณจากค่าที่ไม่ว่าง
- EDA เป็นคำอธิบายชุดข้อมูล ไม่ใช่ข้อพิสูจน์สาเหตุ

การทดลอง:
Train 840 รายการ (ไม่ยกเลิก 642, ยกเลิก 198)
Test 210 รายการ (ไม่ยกเลิก 160, ยกเลิก 50)
เปรียบเทียบ 2 โมเดล: Decision Tree และ KNN
GridSearchCV แบบ Stratified 5-Fold บน Train เลือกพารามิเตอร์ตาม F1 ของกลุ่มยกเลิก
Decision Tree ที่เลือก: max_depth=3, min_samples_leaf=1, class_weight=balanced, random_state=42
KNN ที่เลือก: n_neighbors=5, weights=uniform, p=1 (Manhattan distance)
F1 เฉลี่ยในการ Cross-validation: Decision Tree 53.41%, KNN 35.11% ใช้ผลบน Train นี้เลือก Decision Tree ก่อนรายงาน Test

ผล Test (Precision/Recall/F1 สำหรับ cancelled=1):
Decision Tree: Accuracy 62.38%, Precision 34.07%, Recall 62.00%, F1 43.97%
KNN: Accuracy 73.81%, Precision 40.74%, Recall 22.00%, F1 28.57%
Baseline ทายว่าไม่ยกเลิกทุกคน: Accuracy 76.19%, Recall 0%, F1 0%, Precision ใส่ “—” เพราะไม่มีรายการที่ทายว่ายกเลิก

Confusion Matrix Decision Tree: แถวคือผลจริง คอลัมน์คือผลทำนาย เรียงไม่ยกเลิกก่อนยกเลิก
[[100,60],[19,31]]
TN=100: ไม่ยกเลิกจริงและทายว่าไม่ยกเลิก
FP=60: ไม่ยกเลิกจริงแต่ทายว่ายกเลิก
FN=19: ยกเลิกจริงแต่ทายว่าไม่ยกเลิก
TP=31: ยกเลิกจริงและทายว่ายกเลิก
Recall=31/(31+19)=62%; Precision=31/(31+60)=34.07%
KNN matrix [[144,16],[39,11]] ตรวจพบผู้ยกเลิกจริงเพียง 11 จาก 50

เหตุผลและข้อจำกัด:
Decision Tree มี F1 ใน Cross-validation ดีกว่า KNN และผล Test จับกลุ่มยกเลิกได้มากกว่า แต่แจ้งเตือนผิดมาก ไม่ถือว่าแม่นยำสูง
ข้อมูลสองกลุ่มไม่สมดุล การทายว่าไม่ยกเลิกตลอดได้ Accuracy สูงแต่ Recall=0
Features ยังแยกผลการยกเลิกได้ไม่ชัด ข้อมูลมีขนาดจำกัดและค่าที่ต้องแก้ไข ผลยังขึ้นกับการแบ่ง Train/Test
อาจเพิ่มประวัติการยกเลิก ช่องทางการจอง นโยบายคืนเงินในอนาคต แต่ต้องทราบข้อมูลนั้น ณ เวลาทำนายจริง และเก็บอย่างเหมาะสม
หากทดลองโมเดลอื่นหรือปรับ threshold เพิ่ม ต้องทำบน Train/Validation ไม่ปรับตาม Test ที่เปิดดูแล้ว

เว็บ Streamlit:
หน้า 1 กรอกวันจองล่วงหน้า จำนวนคืน ผู้เข้าพัก คำขอพิเศษ สถานะมัดจำ ประเภทห้อง → กดประเมิน → ดูผลและเหตุผลตามเส้นทางต้นไม้
หน้า 2 สำรวจข้อมูลพร้อมกราฟและคำอธิบาย Features
หน้า 3 เปรียบเทียบโมเดลและ Confusion Matrix
ตัวอย่างสาธิต: lead_days=90, nights=5, guests=2, special_requests=0, deposit_paid=No, room_type=Standard → โมเดลทำนายยกเลิก คะแนนประมาณ 82.2/100 (ไม่ใช่โอกาสจริง 82.2%)
ระบบใช้โมเดล Decision Tree ที่ฝึกไว้ ส่งออกโครงสร้างเป็น model.json และคำนวณผ่าน model_utils.py ผลตรงกับ scikit-learn ใน Test ทั้ง 210 รายการ ไม่ใช่สูตรเดาหรือผลสุ่ม

โครงสร้างสไลด์ 14 หน้า
1. ชื่อเรื่อง ผู้จัดทำ และคำถามหลัก: การจองนี้มีแนวโน้มยกเลิกหรือไม่?
2. ปัญหาและวัตถุประสงค์: ห้องว่างจากการยกเลิก วางแผนห้องพักและติดตามยืนยันการจอง
3. รู้จัก Dataset: จำนวนแถว หน่วยของข้อมูล Target และตารางความหมายทั้ง 8 คอลัมน์แบบย่อ แยกสี Identifier/Feature/Target
4. ตรวจคุณภาพข้อมูล: ค่าว่างแต่ละคอลัมน์ แถวซ้ำ หมวดหมู่ไม่สม่ำเสมอ และตัวอย่างค่าจำนวนที่เป็นทศนิยม
5. Cleaning พร้อมเหตุผล: ก่อน→หลัง 1,062→1,050; strip/lower; ค่าจำนวนผิด→NaN; ทำไมไม่ลบค่าสูงทุกค่า
6. เตรียมข้อมูลเข้าระบบ: แผนภาพที่แสดง Train/Test และ Pipeline ชัดเจน เน้นป้องกัน Data Leakage; One-Hot และ Scaling พร้อมเหตุผล
7. EDA กราฟที่ 1: จำนวนไม่ยกเลิก/ยกเลิก และผลของ Class Imbalance
8. EDA กราฟที่ 2 และ 3: อัตรายกเลิกตามมัดจำ และวันจองล่วงหน้าเฉลี่ย พร้อมข้อค้นพบสั้น ๆ และคำอธิบายว่าไม่ใช่เหตุและผล
9. การสร้างโมเดล: อธิบาย Decision Tree ว่าแบ่งข้อมูลตามเงื่อนไข และ KNN ว่าดูเพื่อนบ้านที่คล้ายกัน พร้อมการแบ่ง 840/210 และ 5-Fold CV เลือกตาม F1
10. ผลเปรียบเทียบ: ตาราง Decision Tree/KNN/Baseline พร้อม 4 metrics และประโยคว่า Accuracy อย่างเดียวอาจหลอกตา
11. Confusion Matrix: ใช้ตาราง 2×2 ที่ระบุแกนชัดเจน ยกตัวอย่างจับได้ 31 จาก 50 และแจ้งเตือนผิด 60 อธิบาย Recall/Precision ด้วยตัวเลขจริง
12. เลือกโมเดลและประเมินความแม่นยำ: เลือก Decision Tree จาก CV F1 ที่ดีกว่า แต่ Test ยังมีข้อจำกัด ไม่กล่าวว่าพร้อมใช้จริง
13. สาธิตเว็บ Streamlit: กรอก 6 ช่อง→กดประเมิน→อ่านผลและเหตุผล ใช้ตัวอย่าง 90 วัน/5 คืน/2 คน/0 คำขอ/ไม่มีมัดจำ/Standard พร้อมอธิบายคะแนนอย่างถูกต้อง
14. สรุปตามเกณฑ์อาจารย์: เตรียมข้อมูลอย่างมีเหตุผล ทดสอบอย่างป้องกัน leakage ข้อค้นพบหลัก ข้อจำกัด และสิ่งที่ควรพัฒนาต่อ 2–3 ข้อ

สิ่งที่ต้องส่งออก

- Speaker notes ทุกหน้า 3–5 ประโยค อธิบายว่า “ทำอะไร / ทำไม / ได้อะไร” และเชื่อมไปหน้าถัดไป
- คำถามที่อาจารย์อาจถามอย่างน้อย 6 ข้อพร้อมคำตอบสั้น เช่น ทำไมตัด booking_id, ทำไมใช้ Median, ทำไม stratify, ทำไม KNN ต้อง Scaling, ทำไม Accuracy สูงยังไม่ดี, ทำไมคะแนน 82.2 ไม่ใช่โอกาสจริง 82.2%
- ใช้ศัพท์อังกฤษพร้อมคำแปลไทยครั้งแรกเท่านั้น จากนั้นใช้คำง่าย
- ตรวจจำนวนและเปอร์เซ็นต์ให้ตรงกับข้อมูลที่ให้ ห้ามเพิ่มผลทดลองเอง
